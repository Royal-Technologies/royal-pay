- Transaction Status

- Receiver Wallet
- Transaction Type

Priority: Fallback

- bKash
- Nagad
- Rocket

Extract:

- Provider
- Transaction ID
- Amount
- Wallet Number
- Sender ID
- Transaction Time
- Payment Reference
- Transaction Type

Store the original SMS only when necessary and under a defined retention policy.

Do not treat an SMS as cryptographic proof of a financial transaction.

# 11. PAYMENT MATCHING ENGINE

Develop a central matching service.

Matching priority:

1. Exact Payment Reference
2. Exact Provider Transaction ID
3. Provider Transaction Reference
4. Wallet and Amount validation
5. Transaction Type validation
6. Transaction Date validation

Amount-only matching must never approve a payment.

## Matching Rules

A transaction may be approved only when:

- Transaction is incoming
- Provider is supported
- Wallet belongs to the tenant
- Amount exactly matches
- Currency matches
- Transaction ID is unique
- Transaction is successful
- Payment Reference is valid where required
- Payment request is still eligible
- No duplicate match exists
- No known reversal exists

Use atomic database transactions and locking for the final payment approval operation.

Ensure only one transaction can pay one payment request and one transaction cannot pay multiple requests.

## Payment Statuses

- pending
- processing
- verified
- matched
- paid
- failed
- unmatched
- duplicate
- review_required
- expired
- cancelled
- reversed
- refunded

Maintain a payment event history.

Never silently overwrite a previous payment state.
